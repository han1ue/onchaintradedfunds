# OTF token economics

The contracts implement the token allocation and claim mechanics described here. The emission schedule is a publisher policy rather than an onchain restriction. The current architecture is unaudited and deployed only on Robinhood Chain Testnet. The active September 5 deployment uses the 15/135 ETH launch curve; the former September 4 deployment remains recorded separately with its original 20/180 ETH parameters.

## Supply and allocation

`OTFToken` is an 18-decimal ERC-20 named `Onchain Traded Funds` with symbol `OTF`. Its constructor mints `MAX_SUPPLY = 1,000,000,000 ether` once. No later mint, tax, blacklist, seizure, or upgrade path exists. Holders can burn their own OTF, and `burnFrom` requires allowance.

`MAX_SUPPLY` records the original issuance. `totalSupply()` records live supply after burns. The deployment script allocates every token and leaves the deployer with none:

| Destination | OTF | Use |
| --- | ---: | --- |
| Team market-cap vesting | 100,000,000 | Ten live-FDV milestones |
| V4 launch manager | 200,000,000 | Bootstrap and permanent liquidity |
| Cumulative rewards distributor | 700,000,000 | 650 million for depositors and 50 million for fund creators, published by multisig |

## Canonical V4 launch

The launch manager creates one OTF/WETH Uniswap V4 pool with a static 0% LP fee and tick spacing 1. It initializes at exactly `0.000000015 WETH` per OTF, which is a 15 ETH reference FDV against the original one-billion-token supply.

The pool price is exact at initialization, while each liquidity boundary comes from V4 `TickMath`:

| OTF/WETH ordering | Exact initialization `sqrtPriceX96` | Bootstrap start tick and boundary | Final tick and boundary |

| OTF is currency0 | 9703428570912459262669889 | -180161 / 9703508046175219238931631 | -158188 / 29110022932210076965716350 |
| OTF is currency1 | 646895238060830617511325894307352 | 180161 / 646889939753375374376401562675059 | 158188 / 215633692560272871859121182412411 |

The exact initialization price sits just outside the starting position boundary. It produces Slot0 tick `-180162` when OTF is currency0 and `180161` when OTF is currency1. The final tick represents approximately `0.000000134997562702653186573 WETH` per OTF, or `134.997562702653186573 ETH` reference FDV. It is `0.002437297346813427 ETH` below the nominal 135 ETH target. The next price-direction tick represents `135.011062458923451891 ETH`, which exceeds the target.

Permanent liquidity is fixed at `18371007233046122951295`, the greatest integer liquidity whose V4 round-up OTF requirement stays within the 50 million cap. It requires `49999999999999999999997973` raw OTF when OTF is currency0 and `49999999999999999999997974` when OTF is currency1, leaving 2,027 or 2,026 raw units below the cap. Increasing liquidity by one would require `50000000000000000000000695` or `50000000000000000000000696` raw OTF, exceeding the cap by 695 or 696 units. Either ordering requires `6749878135132658333` raw WETH.

Bootstrap liquidity is fixed at `27556748080852150400017`, the smallest integer liquidity whose V4 round-down removal returns the permanent position's full `6749878135132658333` raw WETH principal. One less unit of bootstrap liquidity returns one less raw WETH unit. V4 add-liquidity rounding consumes `149997417396300389512897535` raw OTF when OTF is currency0 and `149997417396300389512897549` when it is currency1. Those amounts leave `2582603699610487102465` or `2582603699610487102451` raw OTF units below the 150 million cap. Swap-step round-up across tick-bitmap words makes a boundary purchase consume `6749878135132658377` raw WETH in the currency0 ordering or `6749878135132658378` in the currency1 ordering, 44 or 45 units more than the principal later returned by position removal.

The `afterSwap` hook enforces the full bootstrap corridor using exact sqrt prices. It marks `GraduationReady` only when the pool lands exactly on the final boundary; the inverse ordering reports tick `158187` at the `TickMath(158188)` boundary, so tick equality is not a valid graduation test. Swaps attempted while ready revert.

`OTFLaunchRouter` is the supported bootstrap route. It sets the appropriate boundary price, partially fills an oversized buy or sell, settles only consumed input, leaves unused WETH in the buyer's wallet, and refunds unused native ETH. After the PoolManager returns control, a boundary purchase calls permissionless finalization in the same outer transaction. Any finalization failure reverts the purchase as well.

Ordinary Uniswap UI trades can succeed while they remain inside the corridor. A standard router order that would cross either boundary reverts in full because it cannot supply the required limit. Adding a `beforeSwap` hook would reduce some wasted gas but could not make that order partially fill, so the permanent hook path contains `beforeInitialize`, `beforeAddLiquidity`, and `afterSwap`. After graduation, normal Uniswap trading resumes.

Finalization removes the bootstrap position, measures both returned tokens, and supplies only the derived principal to the permanent full-range position. Donated or unsolicited WETH cannot enlarge it and remains visible as locked dust. Once the permanent mint succeeds, the manager burns its entire OTF balance in one call, including unsolicited OTF. The ordinary burn is `2582603699610487104492` raw OTF in the currency0 ordering and `2582603699610487104477` in the currency1 ordering. The permanent NFT remains owned by the manager, which has no withdrawal or replacement function.

`MAX_SUPPLY` exists only in `OTFToken` and records the original issuance. Launch reference-FDV displays use that value rather than live supply, which falls as OTF is burned.

The four phases are `NotInitialized`, `BootstrapActive`, `GraduationReady`, and `Graduated`. Price movement controls the transition; there is no launch schedule or countdown.

## Team market-cap vesting

`TeamMarketCapVesting` holds 100 million OTF. Only the current beneficiary can checkpoint it. The contract calculates live USD FDV from:

```text
canonical OTF/WETH V4 spot price
× current ETH/USD oracle price
× OTF.totalSupply()
```

The calculation handles either pool currency order and uses full-precision integer arithmetic. It uses current spot price rather than a TWAP. Restricting checkpoints is an explicit trusted-beneficiary design choice; it does not make the spot price manipulation-resistant. The ETH/USD answer must be positive, no older than `maxOracleAge`, and not from the future. Testnet deployment tooling uses a fixed `$2,000` fake oracle; production requires an explicit oracle address.

Each completed $1 million milestone unlocks 10 million OTF, up to $10 million and the full allocation. Values between milestones round down. Once unlocked, a tranche cannot relock after a price or supply decline.

The current beneficiary can claim the cumulative unlocked amount minus prior claims. The beneficiary may nominate, replace, or cancel a successor. The nominee receives claim authority only after accepting; a pending nomination does not interrupt the current beneficiary's authority. A transfer changes neither unlocked nor claimed accounting.

## Immutable fund fees

Each vault creator selects three rates at creation:

| Fee | Default in the application | Contract maximum |
| --- | ---: | ---: |
| Annual creator expense | 0% | 10% / 1,000 bps |
| Mint | 0% | 2% / 200 bps |
| Redeem | 0% | 1% / 100 bps |

The rates and expense beneficiary cannot change. Annual expense accrues through lazy share inflation. Mint and normal redemption fees are also issued as vault shares. Shutdown and final emergency redemptions have no redeem fee. Preview and execution functions share the same arithmetic.

Holding OTF as an accounted vault constituent changes the division of fee shares, not the fee charged to the investor:

```text
creator share = 50% + 40% × sqrt(min(accounted OTF, 10m OTF) / 10m OTF)
buyback share = 100% - creator share
```

| Accounted OTF | Creator | Buyback and burn |
| ---: | ---: | ---: |
| 0 | 50% | 50% |
| 1 million | 62.64% | 37.36% |
| 2.5 million | 70% | 30% |
| 5 million | 78.28% | 21.72% |
| 10 million or more | 90% | 10% |

The contract floors the square-root result to an integer basis-point creator share. Mint and redeem creator portions round down, leaving the remainder for buyback. Annual expense accounting carries its fractional split remainder between checkpoints so checkpoint frequency does not alter cumulative allocation.

The vault checkpoints accrued expense before an operation changes accounted OTF. Direct OTF donations are not accounted and do not affect the split. Fund-owned OTF remains an ordinary constituent and is never burned merely because the vault holds it.

Both portions are minted to `BuybackCollector`. The vault records the exact creator and buyback share counts during the fee transaction. Each factory-recognized vault has a separate collector account, and the collector reads its immutable beneficiary from the vault when settling fees.

## Fee settlement and burn

Only a vault's expense beneficiary can settle its fee account. Settlement checkpoints annual fees, consumes the complete pending creator and buyback share balances, and uses one of two routes:

1. Sell the combined vault shares through approved adapters to canonical WETH.
2. Redeem the shares and sell every constituent to canonical WETH.

The first route may use intermediate tokens, but it must consume the exact pending share balance and leave only WETH as transient output. The caller supplies minimum aggregate WETH, minimum OTF, and a deadline. The collector does not discover routes, calculate fair value, consult an oracle or TWAP, or impose its own slippage value.

Actual WETH is split in proportion to the creator and buyback share counts recorded at accrual. The creator payment rounds down and goes to the beneficiary. Only the remaining WETH may be spent on OTF.

The complete operation is atomic. Fee checkpointing, share sale or redemption, constituent conversion, beneficiary payment, OTF purchase, and burn either all succeed or all revert. A share sale leaves those vault shares outstanding with market counterparties; redemption burns the shares and removes their proportional backing.

The final swap can use only the canonical OTF/WETH V4 pool key. It enforces its own deadline and minimum output, then burns every OTF purchased. The collector has no arbitrary-call, withdrawal, or rescue function. Buybacks may execute during bootstrap or after graduation.

## Cumulative rewards and incentive emissions

`MerkleRewardsDistributor` receives 700 million OTF, 70% of the original one-billion-OTF supply. The incentive policy reserves 650 million OTF, or 65% of the original supply, for depositors and 50 million OTF, or 5%, for fund creators. The combined budget is distributed once a week for exactly four years, or 208 weeks. Emissions stop after week 208.

The weekly target starts at 14 million OTF and declines by approximately 1.968% every week:

```text
weeklyEmission(n) = 14,000,000 × 0.9803203^(n - 1)
```

Each weekly target is divided in the same 65-to-5 proportion as the full rewards budget:

```text
depositorEmission(n) = weeklyEmission(n) × 13 / 14
creatorEmission(n) = weeklyEmission(n) - depositorEmission(n)
```

Week 1 therefore assigns 13 million OTF to depositors and 1 million OTF to creators. Across all 208 weeks, the two buckets must reconcile to exactly 650 million and 50 million OTF.

`n` starts at 1. The factor shown above is rounded for documentation. Applied literally for 208 weeks, it totals approximately 699,999,574.95 OTF, about 425.05 OTF below the fixed allocation. The application uses the rounded formula for weeks 1 through 207 and assigns the remaining allocation to week 208, approximately 229,144.55 OTF, so its schedule model totals exactly 700,000,000 OTF. The reward publisher must apply the same reconciliation or an equivalently precise schedule, then reconcile both weekly buckets to their fixed totals.

The schedule concentrates rewards in the protocol's earliest growth phase and reduces them every week. It has no monthly buckets, quarterly steps, or periodic halvings. The four-year endpoint caps the incentive allocation.

Both buckets use capped pro-rata weights:

```text
cappedWeight(i) = min(eligible OTF balance(i), 10,000,000 OTF)
allocation(i) = bucketEmission × cappedWeight(i) / sum(cappedWeight)
```

The depositor calculation uses eligible deposit balances. The creator calculation uses each fund creator's eligible OTF balance. A balance above 10 million OTF receives no additional weight for that weekly allocation. The publisher determines eligible accounts and balances from the weekly snapshot, applies integer rounding, and keeps the combined allocations within that week's target.

The Funds page shows only the combined weekly distribution. Each fund page shows a fund-specific depositor APY estimate based on the 65% depositor bucket, OTF's current USD value, and that fund's current informational AUM. The estimate annualizes the current weekly value over 52 weeks. A fund with exactly zero AUM uses a labeled $100 calculation baseline without changing the displayed AUM. The estimate is variable, is not guaranteed, and does not determine a user's Merkle entitlement.

The schedule, 65% and 5% split, eligibility rules, and 10 million OTF weight cap are publisher policy. `MerkleRewardsDistributor` does not enforce them. Its owner publishes an immediately active cumulative Merkle root, and the contract defines no reward formula, schedule, delay, or period cap. A valid root can allocate the remaining balance faster than the documented schedule. The owner cannot withdraw reward principal.

Each standard-tree leaf commits to chain ID, distributor address, user address, and cumulative entitlement. Anyone may submit a proof, but payment always goes to the committed user. The distributor records prior claims and transfers only the difference between the proven cumulative amount and the amount already claimed. Invalid proofs, duplicate claims, and decreasing entitlements revert.

Generate an allocation artifact with:

```bash
corepack pnpm rewards:tree -- \
  --input <allocations.json|csv> \
  --output <artifact.json> \
  --chain-id <id> \
  --distributor <address>
```

The script validates addresses, amount syntax, signs, and duplicate users. It does not calculate weekly emissions, split depositor and creator rewards, apply the weight cap, determine eligibility, or reconcile the 700 million OTF schedule.

## Trusted inputs

- The reward-root publisher can allocate the distributor's entire remaining balance through a valid root.
- Each expense beneficiary chooses routes, minimums, and deadlines for its own vault's complete pending fee account.
- The ETH/USD oracle determines one input to live-FDV vesting.
- PoolManager, StateView, PositionManager, Universal Router, Permit2, WETH, adapters, and trading venues execute or report external state used by the protocol.

Production addresses must be supplied explicitly and use official Uniswap V4 deployments. The testnet mirror is accepted only when its runtime code matches the configured hashes.
