# Protocol overview

Onchain Traded Funds (OTFs) are experimental ERC-20 basket vaults. The current pre-mainnet
architecture is oracleless: a creator commits an ordered constituent list and immutable raw-token
bootstrap units for one OTF. The app's fixed `$1` initial basket target, prices, market caps, and
percentage weights stay offchain. The contracts do not calculate NAV, refresh market data, or
rebalance, and the `$1` target is not a peg.

The contracts are unaudited and are not production-ready. `launch/` is a separate prelaunch
competition and is not fund governance.

## Architecture

```text
offchain asset data + creator target/percentages
                  |
                  v
       fixed-point bootstrap calculation
                  |
                  | constituents + raw units only
                  v
             OTFFactory ---- Clones.clone ----> ManagedOTFVault
                  |                                  |
                  |                                  +-- immutable bootstrap basket
                  |                                  +-- accounted-balance settlement
                  |                                  +-- creator expense shares
                  v
         OTFEntryExitRouter ---- approved ITradeAdapter
                                      |
                                      +---- UniswapV3Adapter ---- SwapRouter02
                                      +---- UniswapV4Adapter ---- UniversalRouter ---- PoolManager
```

## Creation application

The connected wallet is the creator. It selects assets while the app uses a fixed `$1` target
initial basket value based on current offchain prices. This calculation target is not a peg or a
guaranteed market price. The app loads current prices, market caps, and token decimals from its
existing offchain asset source. Defaults are market-cap weights normalized deterministically at
18-decimal percentage precision to exactly 100%. Every percentage remains editable, must be
positive, and must produce an exact internal 100% total. Adding or removing an asset preserves all
existing percentages; only the explicit reset action renormalizes the selection.

If every final percentage unit equals that precise default, the creation methodology is
`Market-cap weighted`; any exact-unit difference is `Modified market-cap weighted`. Neutral
fixed-point multipliers compare each final percentage with its market-cap default. These labels
describe initialization only and do not create an ongoing onchain rebalance.

The app uses integer fixed-point arithmetic. With percentage units totaling `T`, fixed target
`V = 1e18` USD WAD, price `P_i` in USD WAD, and token decimals `d_i`:

```text
allocationUsdWad_i = floor(V * percentageUnits_i / T)
bootstrapUnits_i   = floor(allocationUsdWad_i * 10**d_i / P_i)
```

Every raw `bootstrapUnits_i` must be nonzero. The app shows the minimum percentage needed to
produce one raw unit and explains when token precision makes inclusion in a `$1` OTF impossible.
The review step shows the raw quantity, formatted token quantity, and realized percentage after
integer rounding. Prices, market caps, the fixed target, percentages, and weighting methodology
remain application metadata. The trimmed fund thesis, ordered constituents, and calculated
`bootstrapBasketUnitsPerOTF` are included in the onchain creation payload.

After confirmation, the app can associate informational creation metadata with the
vault in the creator browser. If that record is unavailable on a fund detail route, the app shows
`Weighting method unavailable` and does not infer methodology from current balances.

The factory requires a non-empty fund thesis of at most 2,048 UTF-8 bytes. The vault stores it once
during initialization, exposes it through `fundThesis()`, and provides no mutation path. Fund detail
therefore reads the thesis from the vault rather than browser metadata.

`OTFFactory.createVault` uses `Clones.clone`, sets `msg.sender` as creator, and initializes an empty
vault. Creation requires no constituent transfer and has no deterministic address promise.

## Bootstrap and ongoing accounting

Vault shares use 18 decimals. When total supply is zero, the first mint must request at least
`1e16` shares (`0.01` OTF). This minimum is not the calculation denominator. Each required
constituent amount is always:

```text
amountIn_i = ceil(bootstrapBasketUnitsPerOTF_i * requestedShares / 1e18)
```

The first depositor can therefore mint one or multiple OTF units with a proportionally scaled
basket. Once supply is nonzero, later mints use current accounted balances:

```text
amountIn_i = ceil(accountedBalance_i * requestedShares / totalSupply)
```

Normal redemption returns each holder's floored pro-rata accounted balance. A full redemption
returns every accounted balance exactly. A redemption that leaves supply below `1e16`, including
zero, completes and then permanently shuts down the vault. A remaining supply exactly equal to
`1e16` stays live. Shutdown can never be cleared, so a vault that reaches zero through redemption
cannot bootstrap again; minting and fee accrual remain disabled while holder exits stay available.

Holders may call `redeemInKind(shares, receiver, minAmountsOut, skipMask)` directly in both live and
shutdown states, without the router or swap liquidity. For each non-skipped asset, payout is pro
rata from `min(actual, accounted)` while the ledger reduction remains the holder's normal pro-rata
accounted entitlement. Each set bit permanently forfeits that constituent: the vault makes no
external call to the skipped token, reduces its accounted balance by that normal entitlement, and
leaves the physical tokens as permanently unaccounted excess. The skipped minimum must be zero.
This recovery control is intentionally not exposed in the normal application UI.

`accountedBalance` is the vault ledger, not a live valuation. Tracked-token donations do not enter
the ledger. Normal settlement fails closed on a backing deficit. After irreversible shutdown,
permissionless in-kind emergency redemption distributes at most `min(actual, accounted)`.

## Fees, routing, and liquidity

Each vault has an immutable annual creator expense ratio from 0 to 1000 bps and a fixed beneficiary.
Expenses are paid through lazy, cadence-independent share inflation. The factory's immutable
`protocolFeeShareBps` splits fee shares between the beneficiary and `FeeCollector`; there is no
portfolio-dependent rebate.

The permissionless entry/exit router supports ordered generic basket `SwapLeg[]` routes. Legs can
split one token across adapters, accumulate into one output, or spend an earlier leg's output. Each
leg can spend only transient balance above the router's pre-call baseline, so existing dust cannot
fund or be refunded by a route. The router owner is the adapter manager; approval requires a
contract immutably bound back to that router and revocation takes effect immediately.

The approved implementations are `UniswapV3Adapter` and `UniswapV4Adapter`. The V3 adapter accepts only packed V3 paths of at
most three hops, authenticates every pool against its immutable factory, fixes the SwapRouter02
recipient to the entry router, uses exact temporary approvals, and preserves pre-existing adapter
donations. The V4 adapter accepts only typed pool-key paths of at most three hops, authenticates
initialized pools through its immutable StateView, constructs a fixed swap/settle/take action
stream, and clears both ERC-20 and Permit2 allowances. The entry router itself contains no
venue-specific parsing and no direct pool-swap method. Current testnet basket quotes still use only
the cataloged liquid Synthra V3 pools; V4 routing stays dormant until V4 pool keys are configured.

The application Swap product requires an OTF share on at least one side; it is not a general
token-to-token exchange. Production uses the Uniswap Trading API for exact-input BEST_PRICE V3/V4
CLASSIC OTF routes. Robinhood testnet uses the configured Synthra V3 factory, Quoter, SwapRouter02,
and active pools. Basket plans are exact typed router requests and ordered adapter legs. The UI
compares only returned candidates, selects the best queried route by integer output, and performs
exact calldata `eth_call` plus `estimateGas` before submission.

Before accepting a quote whose output OTF has zero supply, the Swap screen reads that supply and
requires the quote's guaranteed minimum output—not merely its expected output—to be at least
`0.01` OTF. There is no first-purchase maximum. Once supply is nonzero, the special quote minimum
does not apply.

The testnet asset catalog distinguishes USDG and WETH quote assets from the five fund constituents.
User swaps allow OTFs only against quote assets or other OTFs. Constituent-to-quote pools are used
internally to settle basket mint/burn routes and by the testnet liquidity utility, not exposed as
general Swap pairs; every configured pool is checked against the Synthra factory and live liquidity.
The separate chain-indexed production catalog only pre-populates convenient assets; it does not gate
the permissionless contracts. Production liquidity is managed at the external venue. `/liquidity`
remains a visibly testnet-only utility for explicitly configured Synthra V3 pools and is not a
production deployment path.

## Verification

The repository runs Solidity formatting, compilation, security gates, unit/fuzz/invariant tests,
coverage reporting, application tests, typechecking, and builds. Passing local or CI checks is not
an audit or deployment approval.
