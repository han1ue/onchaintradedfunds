# Protocol overview

An Onchain Traded Fund is an ERC-20 share token backed by an ordered basket of ERC-20 constituents. The creator fixes the basket, bootstrap units, fee rates, expense beneficiary, and fund thesis at creation. The vault then accounts for deposits and redemptions without an onchain price oracle.

The contracts do not calculate NAV, fetch market data, or rebalance. Prices and weighting labels shown by the application are informational. The protocol is unaudited and not ready for production use.

## Architecture

```text
offchain prices and creator percentages
                  |
                  | ordered constituents + raw bootstrap units
                  v
             OTFFactory ---- clone ----> ManagedOTFVault
                  |                           |
                  |                           +-- accounted constituent balances
                  |                           +-- immutable fee configuration
                  |                           +-- permanent fund thesis
                  v
         OTFEntryExitRouter ---- approved ITradeAdapter
                                      |
                                      +---- UniswapV3Adapter ---- SwapRouter02
                                      +---- UniswapV4Adapter ---- Universal Router
```

`OTFFactory` creates minimal-proxy vaults and records their addresses. `ManagedOTFVault` owns the basket and issues shares. `OTFEntryExitRouter` can convert a single input or basket output through approved adapters, but users can always mint with constituents or redeem in kind without it.

Protocol-token launch, vesting, rewards, and fee buybacks are separate contracts described in [OTF token economics](/token-and-fee-incentives).

During the protocol-token bootstrap, the application routes OTF/WETH buys and sells through `OTFLaunchRouter`. It can stop at either exact range boundary, settle only the consumed input, and refund unused native ETH. Once permanent liquidity exists, protocol-token trades return to the ordinary Uniswap route.

## Creating a vault

The connected wallet becomes the vault creator. `OTFFactory.createVault` accepts:

- name, symbol, and a non-empty fund thesis of at most 2,048 UTF-8 bytes;
- one to 20 ordered constituents and the raw units required for `1e18` shares;
- an expense beneficiary;
- annual expense, mint, and redeem rates capped at 1,000, 200, and 100 basis points.

The factory deploys an empty clone. Creation transfers no constituent tokens and promises no deterministic vault address.

### Application calculation

The application uses current offchain prices, market caps, and token decimals to construct the initial basket. It starts in market-cap-weighted mode. Adding, replacing, or removing a constituent in that mode recalculates all percentages from current market caps. Editing a percentage switches to manual mode; new manual constituents start at 0%, and removing one does not change the remaining manual percentages. Selecting `Market-cap weighted` restores automatic normalization.

Percentages use 18-decimal fixed-point units and must be positive with an exact total of 100%. For target value `V = 1e18` USD WAD, percentage units `w_i`, total units `T`, USD price `P_i`, and token decimals `d_i`, the application calculates:

```text
allocationUsdWad_i = floor(V * w_i / T)
bootstrapUnits_i   = floor(allocationUsdWad_i * 10**d_i / P_i)
```

Every result must contain at least one raw token unit. The application shows the minimum viable percentage and the realized allocation after integer rounding.

The `$1` value is a calculation target for the initial basket. It is not a peg or a guaranteed market price. Prices, market caps, percentages, target value, and weighting method remain offchain. The vault stores only the final raw units and other creation parameters.

The label `Market-cap weighted` applies only when every final percentage unit equals the calculated default. Any difference produces `Modified market-cap weighted`. The creator's browser may retain this metadata after confirmation. If it is unavailable, the fund page reports `Weighting method unavailable` instead of inferring a method from current balances.

## Minting, redemption, and accounting

Vault shares have 18 decimals. The first mint must request at least `1e16` shares, or `0.01` OTF. Required input for constituent `i` is proportional to the fixed bootstrap basket:

```text
amountIn_i = ceil(bootstrapUnits_i * requestedShares / 1e18)
```

After supply becomes nonzero, each mint uses the current accounted balance:

```text
amountIn_i = ceil(accountedBalance_i * requestedShares / totalSupply)
```

A normal redemption pays the floored pro-rata accounted balance of each constituent. Redeeming the full supply returns every accounted balance exactly.

`accountedBalance` is the vault ledger, not the token contract's raw balance and not a valuation. Direct token donations remain unaccounted. Normal mint and redemption fail when actual backing falls below the ledger.

If a redemption leaves total supply below `0.01` OTF, the vault completes that redemption and enters permanent shutdown. A balance of exactly `0.01` remains live. Shutdown disables minting and fee accrual but keeps holder exits available; a vault that reaches zero cannot bootstrap again.

Holders can call `redeemInKind(shares, receiver, minAmountsOut, skipMask)` directly. In shutdown, payouts are limited to `min(actual, accounted)`. A set bit in `skipMask` forfeits that constituent entitlement permanently: the vault reduces its ledger without calling the token and leaves the physical balance as unaccounted excess. The normal application does not expose this recovery control.

## Fees

All three fee rates and the beneficiary are immutable. Annual expense accrues through lazy share inflation. Mint and normal redemption fees also issue shares; shutdown exits are free of redemption fees. Preview and execution functions use the same integer arithmetic.

Fee shares go to `BuybackCollector`. The vault calculates the creator-versus-buyback split from its accounted OTF constituent balance and records both portions when it charges the fee. Later balance changes cannot alter that split, and direct OTF donations provide no benefit.

Only the immutable beneficiary can settle a vault's pending fee account. The beneficiary chooses either a sale of the exact pending vault shares to WETH or an in-kind redemption followed by constituent sales to WETH. The collector pays the creator portion in WETH, routes the remaining WETH through the canonical OTF pool, and burns every OTF purchased. See [OTF token economics](/token-and-fee-incentives#immutable-fund-fees) for the split formula.

## Routed entry and exit

The permissionless entry router accepts ordered `SwapLeg[]` routes. Legs can split an input across adapters, combine outputs, or spend output produced by an earlier leg. A leg can use only balance created during the current call, so pre-existing router dust cannot fund a route or become a refund.

The router owner manages the adapter allowlist. Approval requires adapter code that is immutably bound to that router; revocation takes effect immediately. This owner and every approved adapter are trust boundaries.

The current adapters support Uniswap V3 and V4:

- `UniswapV3Adapter` accepts packed paths of at most three hops and authenticates each pool against its immutable factory.
- `UniswapV4Adapter` accepts typed pool-key paths of at most three hops and checks initialized pools through its immutable StateView.

Both adapters constrain the recipient, use temporary allowances, and preserve balances that existed before execution. The entry router contains no venue-specific path parser and no direct pool-swap method.

### Native ETH boundary

Native ETH is handled only by `mintFromNative` and `redeemToNative`. A native mint requires exact, nonzero `msg.value`, wraps it to the router's immutable canonical WETH, and returns transient WETH change as ETH. Native redemption routes constituents to WETH, enforces the aggregate minimum, unwraps the operation's output, and sends it atomically to the caller.

Vaults, adapter legs, pools, and buybacks never receive native ETH or a native-token sentinel. The router preserves pre-existing ETH and WETH and accepts callback ETH only from canonical WETH.

## Application execution

The Swap application requires a vault share or protocol OTF on at least one side. It is not a general token exchange. Fund pairs may request direct-pool, basket mint, basket burn, or burn-and-mint quotes. The application selects the fresh candidate with the highest integer expected output among the routes it queried and allows manual override.

Production direct quotes use the same-origin Uniswap Trading API integration. Robinhood testnet fund routes use configured Synthra V3 pools, while WETH/OTF uses the canonical V4 pool. The testnet constituent pools support basket settlement and the separate liquidity utility; the Swap interface does not expose them as general constituent pairs.

ETH and WETH remain separate selector assets. The execution plan converts native ETH only at the router boundary, never requests token approval for ETH, and reserves gas when applying Max to a native balance.

Before submitting a selected plan, the application validates the exact sender, target, calldata, value, and route with `eth_call` and `estimateGas`. For an output vault with zero supply, the guaranteed minimum output must be at least `0.01` OTF. This special minimum no longer applies after the first mint.
