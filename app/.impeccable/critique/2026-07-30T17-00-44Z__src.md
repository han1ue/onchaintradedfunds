## Design Specificity Verdict

**The frontend is visually specific but operationally untrustworthy.**

**LLM assessment:** The portfolio-block landing animation, OTF mark, oracle-health language, target-versus-actual allocation model, cooldown, thesis history, and immutable limits feel authored for this protocol. The application is not a generic dark crypto dashboard. Its strongest product character comes from making portfolio change and manager constraints visible.

The operating UI loses credibility when polished financial evidence is not tied to live state. Preview NAV, liquidity, balances, oracle ages, and historical performance are presented with the authority of protocol data. Multiple directory rows also open the same OTF detail, and simulated writes can appear successful without chain evidence. This conflicts directly with the product principle “show evidence, not assurances.”

**Deterministic scan:** The CLI detector returned zero findings for `src`; there were no rule names, file locations, or false positives. That clean result means the primary weaknesses are not generic styling anti-patterns. They are product truth, information architecture, responsive density, and interaction-state problems discovered through visual and behavioral inspection.

**Visual overlays:** Browser mutation failed because the available evaluation surface exposed a read-only document title and could not append a script. No reliable user-visible overlay was created. Browser inspection still covered the landing page, OTF directory, OTF detail, Create, and Documentation, with no browser warnings, errors, or document-level horizontal overflow at the desktop viewport.

## Overall Impression

The landing page makes a strong first promise: this is a protocol for legible, bounded portfolio evolution, not generic token trading. The directory initially sustains that confidence. The experience falls into an avoidable trust valley when synthetic numbers look live, unavailable data sits beside authoritative metrics, and preview interactions behave like working protocol operations.

The biggest opportunity is to make provenance a first-class part of the interface. A less impressive number with a contract address, block, network, and timestamp is more persuasive than a polished metric the user cannot verify.

## Cognitive Load

The review found **five of eight cognitive-load checks failing**, which is high: single focus, chunking, one thing at a time, minimal choices, and progressive disclosure.

Seven visible decision points exceed four concurrent options or information groups: the eight-column directory, six-card detail KPI strip, eight safety limits, five Create asset rows, nine Create safety parameters, the multi-part manager rebalance surface, and the ten-link mobile documentation navigation.

Mobile amplifies the issue. Directory tables retain a roughly 1,040px minimum width, allocation tables remain roughly 760px wide, and the manager workspace becomes an extremely long continuous page instead of a sequence of focused operations.

## Emotional Journey

The landing creates curiosity and confidence because the moving portfolio blocks make changing weights tangible. The directory feels capable and institutional.

The emotional low point is the OTF detail page: production-quality figures coexist with unavailable vault data and no persistent provenance. Create feels reassuring until users can jump to Review, see a blank name and `OTF-`, and receive no explanation for disabled deployment. The manager workspace projects control, then undermines it with editable-looking fields in read-only mode and simulation states that are not grounded in a transaction.

Mainnet and wallet empty states provide the clearest endings because they are candid, bounded, and actionable.

## What's Working

1. **The landing page has real protocol specificity.** The Three.js portfolio blocks communicate changing constituent weights without relying on coins, token logos, or generic network imagery. Reduced-motion and fallback behavior support the concept.
2. **The inspection model is unusually complete.** Allocation, oracle freshness, thesis history, safety limits, cooldown, investor actions, and manager identity are intelligently co-located.
3. **Unavailable states tell the truth.** Mainnet and wallet empty states are restrained, actionable, and aligned with the MVP's actual deployment status.

## Priority Issues

### [P0] Preview data masquerades as live evidence

**Why it matters:** Fixed NAV, liquidity, balances, oracle ages, and `+15.9%` historical performance look verified. Directory rows marked as previews resolve to the same TECH detail. This can mislead investors and breaks the protocol's central promise of inspectability.

**Fix:** Introduce a mandatory `Live`, `Preview`, or `Unavailable` provenance state for every OTF and metric group. Live state must expose network, contract address, block, and last-updated timestamp. Preview state must remain visibly labeled throughout detail pages and must never produce transaction confirmation. Give every preview row its own consistent detail data or remove it.

**Suggested command:** `$impeccable harden the complete frontend`

### [P1] Create permits false progress and offers weak recovery

**Why it matters:** Users can open Safety and Review before valid Basics or Portfolio inputs exist. Completion styling follows the current index rather than section validity, while the disabled deployment action does not enumerate what must be fixed.

**Fix:** Gate future steps, validate each section inline, and derive completion from validity. Keep completed-section summaries visible. On Review, show a linked “Resolve N missing items” list that takes users directly to each invalid field.

**Suggested command:** `$impeccable onboard the Create OTF flow`

### [P1] Navigation and terminology conflict with the product model

**Why it matters:** Landing actions still say “Explore vaults” and “Create a vault,” while investor actions use “Mint.” Internal state-only navigation prevents bookmarking, browser restoration, and direct return to a manager operation.

**Fix:** Standardize investor-facing language around `OTF`, `Deposit basket`, and `Redeem`. Introduce durable routes for `/otfs`, `/otfs/[address]`, `/create`, `/wallet`, and `/otfs/[address]/manage`, preserving network and selected operation where useful.

**Suggested command:** `$impeccable clarify the complete frontend`

### [P1] Mobile keeps desktop information density

**Why it matters:** Wide comparison tables, 9-11px metadata, a long manager workspace, and ten sibling documentation links make essential financial information difficult to scan and operate on a phone.

**Fix:** Replace directory and wallet tables with disclosure rows or intentional mobile card/list compositions. Keep a sticky identifying column where a table is essential. Raise operational text to a 12-14px floor. Split manager operations into focused `Rebalance`, `Roles`, `Fees`, and `Thesis` views.

**Suggested command:** `$impeccable adapt the complete frontend`

### [P2] Action readiness and transaction recovery are opaque

**Why it matters:** Disabled actions do not consistently explain prerequisites. Read-only forms still look editable. Explorer controls are inert, and failed or reverted actions do not provide transaction-level recovery guidance.

**Fix:** Put the unmet requirement adjacent to every disabled primary action. Render non-editable values as values, not disabled inputs. Link confirmed transactions to the explorer, preserve form state after failure, and give specific retry instructions for wallet, network, allowance, oracle, cooldown, and contract reverts.

**Suggested command:** `$impeccable polish the complete frontend`

## Persona Red Flags

**Cautious finance-first investor:** The investor may interpret synthetic performance, protocol NAV, and “connected OTF” language as verified history. Confidence drops sharply when a cooldown or live-read state is unavailable beside those precise figures.

**Protocol manager:** The manager must traverse a very long workspace, cannot return to an operation with a durable URL, and encounters editable controls that may be read-only. The interface does not clearly separate preparation, simulation, wallet approval, and confirmed onchain execution.

**Mobile or low-vision investor:** The investor encounters 9-11px metadata, horizontal financial tables, hidden columns, and long dark surfaces with weak landmarks. Hover-only freshness detail and dense safety information increase the burden further.
